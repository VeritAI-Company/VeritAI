# VeritAI 프론트엔드 최종 정리 (2026-11-06)

## 1. 범위

- 크롬 확장 (`frontend/`)
- PWA 웹 포털 (`portal/`)
- 안드로이드 앱 (`mobile/`, Expo SDK 57, 개발용 빌드)
- 확장과 PWA가 함께 쓰는 공용 코드 (`shared/`)
- 히트맵 상세 설명은 `변경점문서/Readme1029.md` 참고

## 2. 폴더 구조

### 2-1. 공용 코드 `shared/`

- 확장과 PWA가 같이 쓴다
- 앱은 Expo 빌드 구조상 `mobile/` 밖의 파일을 가져올 수 없어서 `mobile/src/`에 같은 내용의 복사본을 둔다
- 판정 기준이나 문구를 바꾸면 `shared` 파일과 앱 복사본을 같이 바꾼다 (같은지 비교하는 테스트 있음)

| 파일 | 역할 | 앱 복사본 |
|---|---|---|
| `judgment.js` | 판정 기준값, 색, 판정 설명, 판정 이유 문구, AI 판정 실패 판별, '판정 없음' 문구 | `mobile/src/judgment.js` |
| `api.js` | 검사 모드, 시간 제한, 결과 조회 간격, 서버 주소 만들기, 서버 상태 문구 | `mobile/src/api.js` 안에 같은 값 |
| `records.js` | 소유자 토큰 만들기, 서버 기록 삭제 순서 | `mobile/src/records.js` |
| `heatmap.js` | 히트맵 영역 고르기, 그리기, 안내 문구 | 없음 (앱은 리포트를 PWA 화면으로 띄움) |

## 4. 판정 표시 규칙

### 4-1. 기준값

- 조작 의심: 얼굴 조작 확률 50% 이상 (빨강)
- 주의: 30% 이상 (주황)
- 정상: 30% 미만 (초록)
- 판정 없음: 얼굴은 찾았지만 그 얼굴의 확률이 없음 (회색, 테두리 번호 옆과 목록에 '판정 없음')
- 인식 신뢰도 50% 미만인 얼굴은 목록에서 처음에 접어 둔다

### 4-2. 판정 이유 문구 (AI 응답의 `decisionReason`)

| 값 | 표시 |
|---|---|
| `high_single_face_probability` | 한 얼굴에서 강한 조작 흔적이 보였습니다 (가장 높은 얼굴 N%) |
| `high_average_face_probability` | 여러 얼굴에서 전반적으로 조작 흔적이 보였습니다 (얼굴 평균 N%) |
| `below_combined_thresholds` (가장 높은 얼굴 50% 이상일 때만) | 단독 기준(80%)보다 낮고 평균도 낮아 정상으로 판정했다는 설명 |
| `full_image_*` (얼굴 0개) | 얼굴을 찾지 못해 사진 전체로 판정, 참고용 |
| `full_image_*` (찾은 얼굴이 모두 `quality.label`이 `poor`) | 찾은 얼굴이 모두 화질이 낮아 분석에서 제외하고 사진 전체로 판정, 선명하고 얼굴이 크게 나온 사진으로 다시 검사 안내 |
| `full_image_*` (그 밖의 얼굴 있음) | 얼굴은 찾았지만 얼굴 영역을 읽지 못해 사진 전체로 판정, 참고용 |
| 그 밖의 값, 예전 응답 | 표시 안 함 |

결과 윗줄도 같은 구분을 쓴다 (`analysisScope`가 `full_fallback`이고 얼굴이 있을 때 "얼굴 N개를 찾았지만 모두 화질이 낮아 / 분석에 쓰지 못해 사진 전체로 검사"). 서버가 화질이 낮은 얼굴을 분석에서 빼는 규칙(`ai/cnn.py`)에 맞춘 것이며, 어느 요소(선명도, 밝기 등)가 나빴는지는 응답에 없어 표시하지 않는다.

### 4-3. AI 판정 실패

- 조건: 응답의 `cnn.modelLoaded`가 `false` (모델 파일, torch, Visual C++ 문제 등)
- 이때 AI 서버는 '확률 0%, 정상'으로 채워 보내므로 판정으로 쓰지 않는다
- 확장: 배지에 'AI 판정 실패 · 다시 시도', 캐시와 통계에 넣지 않음, 콘솔에 원인 출력
- PWA, 앱: 오류 화면에 "AI 판정을 하지 못했습니다. 잠시 후 다시 시도해 주세요." 표시, 개발 빌드에서는 원인도 표시
- 앱: 최근 기록에 남기지 않음, 예전에 저장된 실패 기록을 열어도 같은 오류

## 5. 히트맵 요약

- 영역마다 가장 강한 곳을 빨강으로 맞추고, 상위 20% 칸만 칠한다
- 색의 진하기는 사진 안에서 AI가 많이 본 곳일 뿐, 사진끼리 비교하는 값이 아니다 (조작 가능성은 탭의 %로 본다)
- 처음 여는 탭은 AI가 판정에 실제로 쓴 영역(`winningView`)
- 안내 문구: "얼굴 N 영역의 조작 확률은 N%입니다. 색은 이 영역 안에서 AI가 많이 본 곳이며, 진하기는 사진끼리 비교하는 값이 아닙니다."
- 색 차이가 크게 나는 경우
  - AI가 본 곳이 한두 군데에 모이면 진한 빨강, 고르게 퍼지면 연한 주황
  - 배경이 붉거나 조명이 따뜻하면 색이 섞여 대비가 약해짐
  - 얼굴 영역이 크면 칸이 커지고 흐림도 커져 뭉개져 보임

## 6. 내 기록 지우기 (소유자 토큰)

- 채널마다 처음 검사할 때 64자리 랜덤 토큰을 만들어 저장하고, 검사할 때마다 함께 보낸다
- 서버가 돌려준 검사 번호를 저장해 두고, 지울 때 토큰과 함께 삭제 요청을 보낸다
- 삭제 순서 (`shared/records.js`, 앱은 `mobile/src/records.js`)
  - 100개씩 묶어서 보낸다
  - 서버는 묶음 안에 없는 번호(404), 처리 중인 번호(409), 내 것이 아닌 번호(403)가 하나라도 있으면 묶음 전체를 거절한다
  - 거절되면 한 개씩 다시 지운다
  - 서버에 이미 없음, 내 것이 아님: 정리된 것으로 보고 저장 목록에서 뺀다 (서버 재시작 후에도 실패하지 않음)
  - 처리 중: 저장 목록에 남겨 두고 다음에 다시 지운다
  - 서버 연결 실패: 저장 목록을 그대로 둔다
- 확장의 캐시 비우기
  - 서버 기록 삭제가 성공했을 때만 메모리 캐시와 화면 표시를 지운다
  - 다른 탭에도 알려서 화면 표시를 같이 지운다 (서버 삭제는 한 번만)
  - 오늘 통계는 지우지 않는다

## 7. 서버 연결 상태 표시

- 백엔드의 기존 주소 `/api/detections/queue`로 확인 (백엔드 수정 없음, 4초 안에 응답 없으면 연결 실패)
- 오른쪽에 연결 중인 서버 주소 표시 (배포 주소로 바뀌었는지 확인용)

| 상황 | 문구 | 색 |
|---|---|---|
| 정상 | 분석 서버 연결됨 | 초록 |
| 대기 중인 검사 있음 | 분석 서버 연결됨 · 대기 N건 | 초록 |
| 서버가 작업을 멈춤 | 분석 서버가 검사를 멈췄습니다 | 주황 |
| 30분 안에 AI 판정 실패가 있었음 | 서버 연결됨 · 최근 AI 판정 실패 | 주황 |
| 연결 안 됨 | 분석 서버에 연결할 수 없습니다 | 빨강 |

- AI 모델 상태는 실제 검사 결과로만 알 수 있다 (백엔드에 모델 상태 주소가 없음). 시연 전에는 사진 한 장을 먼저 검사해 본다

## 8. 성능

- 사진이 많은 페이지
  - 사진 번호로 바로 찾는 목록을 두어 페이지 전체 검색을 없앴다
  - 버튼 붙이기를 모아서 한 번에 12ms까지만 처리하고 브라우저에 차례를 넘긴다
  - 겹치지 않는 사진은 가려짐 검사를 건너뛴다
- 화면이 계속 바뀌는 페이지: 변화가 이어져도 최소 0.5초마다 한 번은 처리한다
- 측정 결과 (헤드리스 Chromium, 3회)

| 시험 | 수정 전 | 수정 후 |
|---|---|---|
| 사진 400장, 가장 긴 멈춤 | 1,177 / 1,533 / 3,387ms | 0 / 54 / 0ms |
| 0.05초마다 바뀌는 페이지에 사진 10장 추가, 버튼 붙은 수 | 1장 | 10장 |
| PWA 히트맵 진하기 슬라이더, 1280px 사진 다시 그리기 | 약 1.2ms | 변경 없음 |

- 사진 업로드와 결과 조회의 시간 제한은 세 채널 모두 20초 (`shared/api.js`의 `UPLOAD_TIMEOUT_MS`)
- 추가 측정 (2026-11-11)
  - 확장이 페이지에 주는 부담: 일반 페이지는 거의 없음. 사진 400장 페이지에서만 총 작업 약 1초(스크립트 0.35초, 레이아웃 0.43초), 50ms를 넘는 끊김 없음
  - 검사 1건의 통신량: 업로드 약 300KB(1280px, JPEG 0.92), 서버 응답 약 38KB(얼굴 1개). 이 중 `heatmapBase64`가 약 29KB로 예전 응답 호환용이며, 화면은 `cnn.views[].cam`을 쓴다

## 9. 설정

- 루트 `.env` (확장, PWA 빌드에 쓰임, 예시는 `.env.example`)
  - `VITE_API_BASE`: 분석 서버 주소. 없으면 `http://localhost:8080`
  - 확장 빌드 때 `manifest.json`의 서버 접근 권한도 이 주소로 바뀐다
- `mobile/.env` (예시는 `mobile/.env.example`)
  - `EXPO_PUBLIC_API_BASE`: 분석 서버 주소
  - `EXPO_PUBLIC_PORTAL_URL`: 리포트 화면으로 띄울 PWA 주소
- 확장 권한: `activeTab`, `tabs`, `storage`, `offscreen`, `contextMenus` (쓰지 않던 `scripting`은 뺐다)

## 10. 개발 환경 설치 (포맷 후 재설치 기준)

### 10-1. 설치할 프로그램

| Node.js LTS | 확장, PWA, 앱 | |
| Android Studio | 앱 빌드, adb | SDK Platform 36, Build-Tools 36.0.0, NDK 27.1.12297006 설치 |
| Git | 저장소 | |

### 10-2. 한 번만 하는 설정 (PowerShell)

```
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
setx ANDROID_HOME "$env:LOCALAPPDATA\Android\Sdk"
setx PATH "$env:PATH;$env:LOCALAPPDATA\Android\Sdk\platform-tools"
```

- 설정 후 VS Code를 완전히 닫았다가 다시 연다

### 10-3. 실행 순서

1. AI 서버 (8000번)

```
cd ai
py -3.12 -m venv venv
.\venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r requirements.txt
python main.py
```

- 라이브러리는 `requirements.txt`로만 설치한다 
- Python 버전을 바꿀 때는 venv 폴더를 지우고 새로 만든다

2. 백엔드 (8080번)

```
cd backend\backend_spring
.\gradlew.bat bootRun
```

3. 확장과 PWA

```
npm ci
npm run build
npm run test:frontend
npm run dev:portal
```

- 확장은 `chrome://extensions` → 개발자 모드 → 압축해제된 확장 프로그램 로드 → `dist` 폴더

4. 앱

```
cd mobile
npm run setup
adb reverse tcp:8081 tcp:8081
adb reverse tcp:8080 tcp:8080
adb reverse tcp:5173 tcp:5173
npm start
```

- 폰에 개발용 빌드가 이미 있으면 다시 설치하지 않는다. 앱의 서버 선택 화면에서 `http://localhost:8081`로 접속하거나, Metro 터미널에서 `a`를 누른다
- 다시 빌드(`npm run android`)가 필요한 경우: 새 네이티브 라이브러리 추가, `app.json` 권한이나 플러그인 변경, Expo SDK 변경
- JS 파일과 `mobile/.env` 변경은 `npm start`만 다시 하면 된다
- `adb reverse`는 케이블을 뽑거나 PC를 재시작하면 풀리므로 매번 다시 실행한다
